Hospital Universitario

1 · En una página

Tres piezas, cada una con su trabajo

Todos los sistemas del Hospital Universitario se tienen que ver igual, comportarse igual y estar programados de la misma forma, sin copiarse código entre sí. Para eso hay tres piezas:

Se instala

hu-kit

La caja de herramientas. Los colores, las fuentes y las piezas de pantalla: botones, formularios, tablas, el menú lateral, los avisos.

Cada sistema lo instala con npm. Cuando hu-kit cambia, cada sistema decide cuándo sube de versión.

Se copia una vez

hu-plantilla

El molde. Un sistema vacío pero completo: login, menú, roles, tests y documentación, con hu-kit ya instalado.

Se copia al arrancar un sistema nuevo y después cada uno sigue por su lado. Todavía no existe: es el próximo paso.

Lo propio

Cada sistema

Lo que lo hace único. Sus pantallas, su menú, sus datos, sus reglas: quirofanohu, Bienes HU, el próximo.

Sólo escribe lo suyo: el resto lo trae hu-kit.

La diferencia entre instalar y copiar

Lo que se instala sigue siendo igual en todos los sistemas: si mañana cambia un botón en hu-kit, todos lo reciben al subir de versión. Lo que se copia es un punto de partida que cada sistema después adapta, como sus roles o su menú. Una pieza va a hu-kit cuando tiene que seguir igual; va a la plantilla cuando alcanza con que arranque igual.

El catálogo: la vidriera de hu-kit

Es una página que vive dentro de hu-kit y muestra armadas todas las piezas, una al lado de la otra, en claro y en oscuro. No tiene base de datos ni login: los datos son inventados. Sirve para mirar qué hay antes de armar una pantalla, para probar un cambio en hu-kit sin instalarlo en un sistema, y de ahí salen las capturas de esta guía. 

cd C:\laragon\www\hu-kit
npm install          (la primera vez)
npm run catalogo     (y abrir en el navegador la dirección que muestra)

4 · Un sistema nuevo

Arrancar «Farmacia HU»

Supongamos que hay que hacer un sistema nuevo para Farmacia. Así se arranca.

Con hu-plantilla · cuando exista

  1. En GitHub, en mauroas7/hu-plantilla, tocar «Use this template» y crear el repo farmaciahu.
  2. Clonarlo e instalarlo: 
    git clone https://github.com/mauroas7/farmaciahu.git C:\laragon\www\farmaciahu
cd C:\laragon\www\farmaciahu
composer install
copy .env.example .env
php artisan key:generate
php artisan migrate --seed
npm install
npm run dev
  3. Abrir http://farmaciahu.test (Laragon lo publica solo): ya aparece el ingreso del HU, con el menú lateral y el modo oscuro andando.
  4. Cambiar las cinco cosas propias del sistema:
    • el nombre, en .env (APP_NAME);
    • el texto del ingreso, en Components/UI/PanelDeIngreso.jsx;
    • las opciones del menú, en data/navegacion.js;
    • los roles, en app/Enums/Rol.php;
    • el README.md.
  5. php artisan test tiene que dar verde: trae los tests que vigilan las convenciones.
  6. Para la primera pantalla, abrir el catálogo, elegir las piezas y armar la página con ellas. No hay colores ni estilos que decidir.

El puente: el AppLayout de cada sistema

MarcoApp no sabe nada de un sistema en particular: recibe el menú, el usuario y los enlaces ya armados. Cada sistema tiene un AppLayout de unas 25 líneas que se los pasa, y sus páginas usan sólo ese AppLayout. 

// resources/js/Components/UI/AppLayout.jsx
import { usePage } from '@inertiajs/react';
import { MarcoApp, rutaActiva } from 'hu-kit/componentes';
import { seccionesDelRol } from '@/utils/secciones';

const SISTEMA = { nombre: 'Farmacia HU', bajada: 'Pedidos y stock de farmacia' };

export default function AppLayout({ titulo, subtitulo = null, ancho = 'completo', children }) {
    const { usuario } = usePage().props.auth;

    // El menú es de cada sistema: acá se filtra por rol y se le pone a cada opción su dirección.
    const secciones = seccionesDelRol(usuario?.rol).map((seccion) => ({
        ...seccion,
        href: seccion.ruta && route(seccion.ruta),
        activa: Boolean(seccion.ruta) && rutaActiva(seccion.activaEn ?? seccion.ruta),
    }));

    return (
        <MarcoApp
            titulo={titulo} subtitulo={subtitulo} ancho={ancho}
            secciones={secciones}
            inicio={route('inicio')}
            sistema={SISTEMA}
            usuario={usuario && { nombre: usuario.nombre, email: usuario.email, rol: usuario.rolEtiqueta }}
            enlaces={[{ etiqueta: 'Mi cuenta', icono: 'manage_accounts', href: route('cuenta') }]}
            salir={route('logout')}
        >
            {children}
        </MarcoApp>
    );
}
// resources/js/data/navegacion.js: el menú, sin lógica
export const SECCIONES = [
    { etiqueta: 'Tablero', icono: 'monitoring', ruta: 'tablero', roles: ['farmacia'] },
    { etiqueta: 'Pedidos', icono: 'list_alt', ruta: 'pedidos.index', activaEn: 'pedidos.', roles: [] },
    { etiqueta: 'Usuarios', icono: 'manage_accounts', ruta: 'admin.usuarios.index', titulo: 'Administración', roles: ['admin'] },
];

Lo que el backend tiene que compartir

HandleInertiaRequests::share() manda auth.usuario (con id, nombre, email, rol y rolEtiqueta) y flash con exito, error, aviso e info. Con eso andan el marco, el menú de la cuenta, el modo oscuro y los avisos.

5 · Un sistema que ya existe

Acoplar hu-kit: el caso de Bienes HU

Bienes HU ya usaba hu-kit, pero tenía su propio menú lateral, copiado de quirofanohu, que en dos días ya se había separado del original. Con la versión 1.8.1 ese marco pasa a hu-kit. Así se hizo, paso a paso:

Paso Quién Qué pasa
1Quien mantiene hu-kitArma las piezas nuevas y las mira en el catálogo, en claro y en oscuro.
2Quien mantiene hu-kitInstala en el sistema una versión de prueba, sin publicar, y cambia sus archivos (tabla de abajo).
3Los dosPrueban que compile, que pasen los tests y que el sistema se vea igual que antes. Si algo falla, se corrige en hu-kit y se repite el paso 2.
4Quien mantiene hu-kitPublica la versión: commit, tag v1.8.1 y push. Un tag publicado no se mueve nunca.
5Quien trabaja en el sistemaApunta el sistema a la versión oficial y hace su commit.

Los comandos

REM paso 2, la versión de prueba (desde hu-kit y desde el sistema)
npm pack --pack-destination %TEMP%
npm install %TEMP%\hu-kit-1.8.1.tgz
npx vite --force

REM paso 5, la versión oficial (desde el sistema)
npm install hu-kit@github:mauroas7/hu-kit#v1.8.1

6 · El día a día

Trabajar con hu-kit

Hacer una pantalla

Abrir el catálogo, buscar las piezas que hacen falta e importarlas. Si una pantalla del catálogo se parece a la que vas a hacer, copiá su forma: está en catalogo/ejemplos/.

Falta una pieza

La pregunta es una sola: ¿la va a usar otro sistema?

Sí → va a hu-kit

Se agrega en componentes/, con su ejemplo en el catálogo, su fila en el README y su entrada en el CHANGELOG. Se publica una versión nueva y el sistema la instala.

No → queda en el sistema

Se hace en resources/js/Components/ del sistema, armada con piezas de hu-kit. Si después aparece en un segundo sistema, recién ahí sube.

Lo mismo con un color: si falta un tono, se agrega con nombre en hu-kit. Nunca un color escrito a mano (bg-[#…]).

Subir la versión de hu-kit en un sistema

npm install hu-kit@github:mauroas7/hu-kit#vX.Y.Z
npm run build
php artisan test

Antes, leer en el CHANGELOG de hu-kit qué trae la versión y si pide algo «al subir». Cambiar el número a mano en package.json no alcanza: el lock se queda con la versión vieja.

Publicar una versión de hu-kit (quien lo mantiene)

  1. Probarla en un sistema con la versión de prueba (npm pack), como en el paso 2 de la sección anterior.
  2. Subir version en package.json y anotar la versión arriba de todo en CHANGELOG.md.
  3. Si cambió alguna pieza, npm run guia vuelve a sacar las capturas y este PDF.
  4. Commit, tag anotado con el mismo número y push: git tag -a vX.Y.Z -m vX.Y.Z y git push origin main vX.Y.Z.
  5. Si cambiaron las skills de Claude, volver a correr instalar.ps1.

Un error en una versión publicada se arregla publicando la siguiente: un tag no se mueve ni se borra.

Dónde va cada cosa

Si lo que vas a agregar es… Va en

La marca, en cinco reglas

primary · #003764
Pantone 2955 C

secondary · #C7A36E
Pantone 465 M

brandText · #59595B
El gris del logotipo

  1. Tres colores, y sus derivados con nombre. Nunca un color escrito a mano. Todo texto llega a un contraste de 4,5:1: el dorado sobre fondo claro es secondary-dark.
  2. Montserrat, en tres pesos: 400, 600 y 900 (font-normal, font-semibold, font-black). Nunca font-bold ni font-medium.
  3. Dos formas de botón: redondo del todo para confirmar o enviar; esquinas de 12 px para navegar o elegir.
  4. Íconos Material Symbols Outlined: rellenos sólo en la sección en la que estás parado.
  5. Español rioplatense, con voseo: «podés», «tenés», «elegí». Frases cortas, sin signos de exclamación.
